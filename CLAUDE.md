# CLAUDE.md

Нотатки для Claude Code при роботі з цим репозиторієм. Проєкт описаний у README.md — тут лише те, що корисно знати для внесення змін.

## Що це за код

Два великі однофайлові HTML-модулі й shell, який уже почали мігрувати на Vite + TypeScript:
- `index.html` — shell з PIN-входом і табами, вантажить інші два модулі в iframe; runtime-логіка винесена в `src/shell.ts` і підключається як Vite module script.
- `osbb/index.html` — Виконані роботи + Ліфтер, Сміття, Зміни, Табель. Акцент — зелений (`#34c759` світла тема / `#30d158` темна). **Журнал чергувань і Графіки видалені повністю в липні 2026** (застаріла модель — вільний текст замість заявок з пріоритетом) — не відновлювати, не шукати `#section-journal`/`#section-charts` як щось загублене. **Вкладка «Заявки» (Jira, `#section-my-tickets`) видалена в жовтні 2026** на прохання користувача — не відновлювати. Усі розділи журналу доступні всім сесіям, крім «Змін» (закриті для робітників).
- `sklad/index.html` — Склад: товари, видача, інвентаризація. Теж зелений акцент (уніфіковано в липні 2026, раніше був синій).

Логіка всіх трьох модулів живе в `src/` (Vite MPA build, `npm run build` → `dist/`, деплой на GitHub Pages через `pages.yml`). HTML-файли — лише розмітка. Компонентного фреймворку немає; не переносити на React/Vue/Svelte без явного запиту.

### `src/*.ts` ↔ `src/*.js` (вересень 2026)

- Браузер і unit-тести використовують `src/*.js`; `tsc` перевіряє `src/*.ts`.
- **TS — джерело істини** для модулів із реалізацією в `.ts`: їхні `.js` **генеруються** `npm run build:js` (`scripts/build-js-fallback.mjs`, esbuild) і мають шапку `// Згенеровано з src/...`. Не редагувати ці `.js` вручну — `test:runtime` вимагає байт-у-байт збіг зі згенерованим.
- **JS — джерело істини** лише для `src/osbb-app.js` / `src/sklad-app.js` (без `.ts`, правити руками). З вересня 2026 усі контролери — повноцінний TS (shim-ів `export declare function` більше нема; не повертати їх). Спільні DI-типи контролерів (`SupabaseLike`, `ToastFn`, `KeyValueStorage`…) — `src/controller-types.ts`.
- Smoke-check шукає в `.ts`-джерелі точні рядки з анотаціями типів (`function select(button: HTMLElement)`) — при зміні сигнатури оновлювати й голку в `scripts/smoke-check.mjs`.
- Smoke-check і `tests/sklad-dom-flows.test.mjs` читають для згенерованих `.js` їхнє `.ts`-джерело.
- Сторонні бібліотеки — npm-залежності з фіксованими версіями (`@supabase/supabase-js`, `xlsx`, `html5-qrcode`, `chart.js`), не CDN. `xlsx`/`html5-qrcode`/`chart.js` вантажаться лениво (`await import(...)`). `xlsx@0.18.5` має CVE лише для **читання** файлів — у проєкті тільки запис; якщо колись з'явиться імпорт Excel, спершу оновити бібліотеку.

## Усталені патерни дизайн-системи (не винаходити заново)

- **Кастомний `<select>`**: нативний select рендериться браузером як квадратне непіддатливе спливне меню. `enhanceSelect(select)` / `refreshEnhancedSelect(select)` тепер живуть в одному місці — `shared/enhance-select.js` (звичайний `<script src>`, без бандлера), підключені і в journal, і в sklad. Не дублювати їх назад inline — smoke-check це ловить. Обгортає прихований `<select>` кастомною заокругленою панеллю (`.custom-select-wrap/-btn/-panel/-option`), з підтримкою клавіатури (Enter/Space/стрілки/Escape) і опційним пошуком через `data-searchable="1"`. Якщо десь ще лишився голий `<select>` — використовувати той самий патерн, не робити новий.
- **Спільні CSS/JS без бандлера**: `shared/ui.css` (тултіпи `[data-tip]`, `prefers-reduced-motion`) і `shared/enhance-select.js` — єдине місце для того, що реально ідентичне між модулями. Не все дублювання варто виносити сюди: якщо модулі розійшлись у поведінці (як було з `enhanceSelect` до липня 2026, коли Sklad додав пошук), спершу звести докупи функціонально, а не сліпо взяти першу-ліпшу копію.
- **Тултипи**: `[data-tip="текст"]` замість `title=` — CSS-псевдоелемент, заокруглений темний пільс замість системного. Клас `.tip-up` — якщо кнопка всередині `overflow:hidden` контейнера (напр. в таблиці), щоб підказка відкривалась вгору і не обрізалась.
- **Skeleton-заглушки завантаження**: клас `.skel`/`.skel-bar` (shimmer-анімація) замість тексту "Завантаження..." — використовується як статичний початковий HTML у `<tbody>`, перезаписується реальним рендером.
- **Плаваюча нижня навігація** (мобільна): `#bottom-nav` / `.bottom-nav` — не суцільна смуга по краю, а картка з відступом `12px` з усіх боків, `border-radius: 26px`, тінь. У osbb позиціювання йде через Tailwind-класи (`fixed bottom-0 left-0 right-0`), тому кастомні CSS-правила для нього **обов'язково з `!important`**, бо мають перебити Tailwind-утиліти.
- **Іконки**: Shell і журнал використовують `Material Symbols Rounded` через `.material-symbols-rounded`; Sklad використовує той самий шрифт через сумісний клас `.ms`. Для нових інтерфейсних іконок використовувати офіційні назви Material Symbols, без сторонніх SVG або MDI.
- **Material Design 3 — свідомий вибір напряму дизайну, не разова примха.** Користувач прямо попросив (липень 2026) дотримуватись MD3 і в майбутніх сесіях — окремо підкреслив, що йому подобаються **контури** (outlined-стиль). На практиці це означає:
  - `shared/material-tokens.css` — спільний semantic token layer для shell/journal/sklad (`--md-sys-color-*`, `--md-sys-shape-*`, `--md-sys-typescale-*`, elevation, motion, state-layer). Нові UI-полірування починати з використання цих токенів, а не додавати чергові hardcoded кольори/радіуси/тіні (напр. пріоритет замість `#f59e0b` — `var(--md-sys-color-tertiary)`, він сам адаптується під світлу/темну тему).
  - Картки/поля вводу/пункти списків — з видимим бордером. Для елементів, які мають читатись як самостійний outlined-компонент (картка статистики, пункт вибору, поле вводу) — `border:1px solid var(--md-sys-color-outline, var(--border))` (виразніший контур), а не ледь помітний `--md-sys-color-outline-variant` (той — для менш акцентних внутрішніх розділювачів/контейнерів-обгорток).
  - Кожен новий "голий" `<select>` — обов'язково через `enhanceSelect()` (див. пункт вище), інакше він рендериться нативним квадратним попапом, що ламає стиль. Те саме стосується `<input type="time">` — нативний "Засіб вибору часу" непіддатливий і не стилізується; замість нього використовувати маскований текстовий інпут `ГГ:ХХ` (`data-time-mask` + `formatTimeMaskInput`, вже є для журналу сміття й табеля).
  - Interactive-елементи (кнопки, пункти списку, картки-кнопки) — з класом `.md-state-layer` для стандартного hover/focus/pressed ripple-шару, і `:focus-visible` для клавіатурного фокусу (див. нижче) — не пропускати ні на одному новому елементі.
- **Фокус з клавіатури**: `outline:none` було глобально вбито без заміни — тепер скрізь є `:focus-visible { outline: 2px solid ... }`. Не видаляти ці правила.
- **`prefers-reduced-motion`**: є `@media (prefers-reduced-motion: reduce)` у всіх трьох файлах — глушить анімації/переходи.

### Журнал сміття: збереження по днях (`030`)

- `save_garbage_day(p_month_key, p_day, p_row)` оновлює один ключ дня. Цілий місяць через `upsert` пишеться лише при міграції старого формату.

## Специфічно для Журналу (osbb): staff auth, ролі, Табель, пріоритет заявок

Липень 2026 — великий рефакторинг журналу: прибрано вільнотекстовий "Журнал чергувань" і чат, додано персональний per-worker вхід поверх спільного PIN, Табель точного часу і пріоритет заявок.

- **Ролі** (`osbb_staff.role`): `dispatcher`, `admin`, `board` ("Правління", необмежений доступ крім Змін) — рівнозначні "повний доступ"; `plumber`/`janitor`/`electrician` — робітники, view-only календар + власні заявки. Ролі "охорона" нема і не додається навмисно (просили прибрати на початку рефакторингу).
- `isDispatcherSession()` (`src/osbb-staff.ts`, обгортка в `src/osbb-app.js`) — єдине джерело істини, чи сесія має повний доступ: `['dispatcher','admin','board'].includes(staffSession.role)`. `WORKER_ROLES = ['plumber','janitor','electrician']`. `isTabAllowedForSession(tab)` — єдине джерело істини для видимості табів І для блокування прямого виклику `setTab()`/`requestTab()` — не дублювати цю перевірку окремо десь ще (був баг: гейтинг рахувався в двох місцях по-різному).
- **staffSession vs staffPinCache**: `staffSession` (хто ти — id/name/role) живе в `sessionStorage`, переживає reload вкладки. `staffPinCache` (сам PIN) — навмисно **тільки в пам'яті**, ніколи в storage. Наслідок: після reload сесія лишається, а PIN губиться — будь-яка дія, що вимагає server-side PIN (Табель), впаде без явного повторного логіну. Патерн виправлення — `requestStaffReauth()`: короткий екран підтвердження PIN (без вибору зі списку, особа вже відома), не скидає staffSession, тільки оновлює `staffPinCache`. Використовувати цей самий патерн для будь-якої майбутньої дії, що потребує `staffPinCache` і може викликатись після reload.
- **Табель** (`osbb_attendance`, `save_attendance_day` RPC) — точний час приходу/відходу трьох робочих ролей за день, редагує лише dispatcher/admin/board (перевірка **на сервері** всередині RPC через `verify_staff_pin`, не тільки на клієнті). Автопідрахунок годин/днів — локально з `checkIn`/`checkOut`.
- **Пріоритет заявок**: `ticketPriorities = {HIGH,MEDIUM,LOW}` на кожному тікеті в `dispatcher.ticketsList`. Рендериться кольоровим CSS-кружком `.priority-dot`, **не emoji** (користувач явно просив прибрати емодзі-бейджі як негарні — лишились тільки в тексті `<option>` нативного select, бо туди HTML не вставити). "Мої заявки" — сортування робітника за пріоритетом, може закрити тікет з фото/коментарем. Адмін/диспетчер може редагувати вже створену заявку (`dispEditingTicketId`), не тільки додавати/видаляти.
- **Ліфтер** (`elevator_visits`) — окремий невеликий блок усередині вкладки «Виконані роботи» (не окремий таб): відмітки приїзду ліфтера кілька разів на місяць, день + текст що зробив, без календарної сітки.

### Технічний урок: `jsonb_set` не створює проміжні рівні шляху

Знайдено й виправлено в липні 2026 (`018_fix_attendance_jsonb_set.sql`) — вартий запам'ятати як загальний Postgres-готча, не специфічний тільки для Табеля: `jsonb_set(doc, array['a','b'], value, true)` **не створює `'a'`**, якщо його ще нема в `doc`, навіть з `create_missing = true` — той параметр створює лише **останній** елемент шляху, за умови що всі попередні вже існують. Перевірено напряму на Postgres 16:
```sql
select jsonb_set('{}'::jsonb, array['5','plumber'], '{"x":1}'::jsonb, true); -- {} (без змін!)
```
Наслідок був підступний: RPC повертав `true` (ніби успіх), а дані мовчки не зберігались — доки день хоч раз не отримає перший запис якимось іншим шляхом. Правильний патерн для дворівневого jsonb-стану "по днях": будувати вкладений об'єкт заздалегідь і `jsonb_set` лише на **один** рівень:
```sql
jsonb_set(doc, array[day_key], coalesce(doc->day_key, '{}'::jsonb) || jsonb_build_object(role, value), true)
```
Будь-де в проєкті, де jsonb-стан має вкладеність >1 рівня і оновлюється через `jsonb_set` з масивом шляху довжини >1 — перевіряти цю пастку, а не довіряти `create_missing`.

## Специфічно для Складу

- Товар можна позначити `is_internal` (внутрішнє використання/хознужди) — не входить у "баланс складу" на сторінці Статистика. Перемикається іконкою в рядку товару (`toggleInternal(id, val)`), фільтрується пілками "Без внутрішніх" / "Тільки внутрішні" (взаємовиключні, `hideInternal`/`onlyInternal`).
- **Облік вартості товарів додано як опційний**: `sklad/supabase/004_add_price_tracking.sql` додає поля ціни до `inventory_items`; ціну можна вказати вручну або під час оприбуткування надходження.
- Схема Supabase (`inventory_items` та ін.) керується вручну через SQL-скрипти в `sklad/supabase/*.sql`, які користувач виконує в Supabase SQL Editor. **Якщо додаєш нову колонку і фронтенд одразу починає її використовувати в INSERT — попередь користувача, що без виконання SQL-міграції ця дія (напр. "Додати товар") почне падати з помилкою.** Так було з `003_add_internal_use_flag.sql`. Для цін INSERT не змінювали — без `004_add_price_tracking.sql` падає тільки збереження ціни, не додавання товару.

## Відомі обмеження / свідомо прийняті ризики

Щоб наступний аудит (людський чи AI) не "відкривав" це заново як несподівану знахідку — нижче задокументовані речі, які вже відомі й свідомо прийняті для поточного масштабу (один будинок, кілька співробітників), а не проґавлені баги:

- **RLS відкритий на insert/update для anon/authenticated** на "робочих" таблицях (`garbage`, `photos`, `inventory_items`, `inventory_logs`, `inventory_receipts`, `inventory_audits`, `inventory_audit_items`) — `using(true)`/`with check(true)`. Anon-ключ вшитий у публічний HTML. Обґрунтування: маленька довірена команда, PIN-екран — єдиний бар'єр перед UI, не перед даними напряму. Якщо масштаб зросте (більше будинків/користувачів) — це треба переглянути (RPC-обгортки або Supabase Auth), але зараз свідомий компроміс, не проґавлена діра.
- **Ліміт спроб PIN — по IP (`033`, `pin_throttle`)**: ключ — заголовок `cf-connecting-ip` (Cloudflare перезаписує його і блокує клієнтську підробку; перевірено на живому проєкті у вересні 2026), резерв — `sb-forwarded-for`. `X-Forwarded-For` **не використовувати** — клієнт дописує туди що завгодно. 5 помилок з IP → блок цього IP (5 хв → 15 хв → 1 год → 4 год); 30 помилок за 15 хв з будь-яких IP → блок для всіх на 10 хв. Відомий нюанс: `jira-issues` викликає `verify_staff_pin` з Edge Function, тож там усі користувачі ділять IP функції.
- **PIN — не per-user авторизація.** Один спільний PIN на весь застосунок (два — для журналу: вхід/скидання). Нема аудиту "хто саме зробив дію" — поля `author`/`issued_to`/`person` це вільний текст від користувача, не перевірена особа.
- **Telegram bot-токен зберігається в таблиці `telegram_config`**, не в Supabase Edge Function secrets — це свідомий вибір (простіше міняти chat_id/токен без редеплою функцій), не помилка. Але через це RLS на `telegram_config`/`osbb_telegram_config` **обов'язково має бути без жодної policy** (default-deny) — інакше токен читається anon-ключем. Так уже сталося один раз у видаленому проєкті журналу; при будь-якій зміні цих таблиць перевіряти, що policy не додались випадково.
- **Приклад-PIN у git — станом на липень 2026 підтверджено все ще не замінений на реальний** (жива база досі приймає той самий приклад-PIN, що прописаний у `sklad/supabase/001_setup_pin_auth.sql` і `005_merge_osbb_journal.sql` — самі цифри свідомо не повторюємо тут ще раз, вони й так у git-історії тих SQL-файлів, нема сенсу множити копії). Користувач свідомо відклав заміну ("поміняємо потім") — не забувати нагадувати, не намагатись замінити самому без прямого запиту (новий PIN не повинен з'являтись у логах сесії агента, міняти має сам користувач через SQL Editor).
- **Демо-PIN staff-акаунтів так само не замінені** — `014_journal_staff_auth.sql` (дисп./сантехнік/двірник/електрик) і `015_add_board_role.sql` (Правління) вставляють приклад-співробітників з заглушковими PIN — самі цифри теж свідомо не повторюємо тут, вони в git-історії цих файлів. Той самий принцип: не міняти самому без запиту, лише нагадувати.
- ~~Немає атомарності на списанні складу~~ — **виправлено в липні 2026**: `issue_item`/`receive_item` RPC (`sklad/supabase/006_atomic_stock_issue_receive.sql`) роблять `UPDATE ... WHERE quantity >= qty` і вставку логу в одній транзакції на сервері. `sklad/index.html` більше не читає залишок з клієнтського кешу для перевірки — викликає RPC і реагує на помилку `insufficient_stock`.

## Тестування в цьому пісочничному середовищі

- Вихідний трафік до `fonts.googleapis.com` і Supabase заблокований проксі. Tailwind для `osbb/index.html` компілюється локально через Vite; production build більше не залежить від `cdn.tailwindcss.com`. Для повної візуальної перевірки Журналу використовувати Vite build/preview, а не сирий static server, бо `osbb/tailwind.css` є build entrypoint.
- Робочий спосіб візуальної перевірки: `npm run build` і статичний сервер, що віддає `dist/` під префіксом `/Osbb/` (сирий `python3 -m http.server` більше не підходить — `src/*-app.js` імпортують npm-пакети, які резолвить лише Vite) + Playwright (`executablePath: '/opt/pw-browsers/chromium'`) + `page.addInitScript(() => sessionStorage.setItem('auth','ok'))` щоб проскочити PIN-екран. Playwright треба імпортувати з `/opt/node22/lib/node_modules` (глобальний пакет), інакше `Cannot find package 'playwright'`.
- Завжди запускати `node scripts/smoke-check.mjs` після правок — станом на липень 2026 це 176+ перевірок критичних RPC/PIN-flow/SW/shared-файлів; число росте з кожною правкою, не орієнтуватись на конкретну цифру, орієнтуватись на "усі мають бути ok". Повний прогін — `npm test` (typecheck, генерація/паритет JS, MD3-перевірки, unit, міграції, функції, smoke). Після правки будь-якого `src/*.ts` — `npm run build:js`.
- Через відсутність збірки легко зламати HTML мовчки (незакритий тег) — після великих правок перевіряти баланс тегів: `python3 -c "data=open('FILE').read(); print(data.count('<div'), data.count('</div>'))"` для div/svg/button/label.

## Відкриті питання на наступну сесію (липень 2026)

- **Multi-tenancy (`building_id`)** — користувач підняв питання, чи вводити поле для кількох будинків. **Не робити без явного запиту**: зараз RLS навмисно відкритий (`using(true)`) для anon в межах одного будинку (див. "Відомі обмеження" вище) — додати колонку `building_id` без реальної ізоляції (auth.uid() + членство в будинку замість спільного PIN) нічого не захистить, лише створить ілюзію multi-tenancy. Перш ніж починати — уточнити в користувача, чи справді з'являється другий будинок/клієнт, бо інакше це велика робота "про запас".
- **Storybook / візуальні тести** — вимагає компонентного фреймворку (React/Vue/Svelte). Мінімальний build-step для shell уже є, але osbb/sklad ще не компонентні, тому Storybook поки нема для чого показувати. Зараз немає окремих UI-компонентів, тільки величезні HTML-файли з дублюванням розмітки — Storybook самим собою нема для чого показувати. Реальний передумовний крок — набагато глибша компонентизація, тижні-місяці роботи, не "додати інструмент за раз".
- **PIN не замінений** — див. "Відомі обмеження" вище.
- **Перевірити, чи виконані на живій базі SQL-файли `sklad/supabase/014`–`018`** (staff auth/Табель, роль board, лог ліфтера, два фікси `save_attendance_day` — роль board і `jsonb_set`-баг). Якщо користувач знову скаже "щось не зберігається" в Табелі — перше питання: чи виконані саме ці файли, а не одразу шукати новий баг у коді.
