# CLAUDE.md

Нотатки для Claude Code при роботі з цим репозиторієм. Проєкт описаний у README.md — тут лише те, що корисно знати для внесення змін.

## Що це за код

Два великі однофайлові HTML-модулі й shell, який уже почали мігрувати на Vite + TypeScript:
- `index.html` — shell з PIN-входом, вантажить інші два модулі в iframe; runtime-логіка винесена в `src/shell.ts` і підключається як Vite module script.
- **Єдина навігація (листопад 2026)**: меню всіх розділів живе лише в shell (`src/shell-nav.ts` — список розділів; `#shell-nav` бічна панель ≥641px, `#shell-bottom-nav` + лист `#shell-more-sheet` на телефоні). Shell шле в iframe `{type:'osbb:navigate', section}`, модуль відповідає `{type:'osbb:section-changed', section}`; перше відкриття модуля — `?embed=1&section=…`. У shell модулі отримують клас `html.in-shell` і **ховають власні таби/бічну панель/нижнє меню** — поза shell (пряме відкриття `osbb/` чи `sklad/`) вони працюють як раніше, не видаляти їхню навігацію. «Зміни» через URL не відкриваються (PIN) — лише через `requestTab`.
- **Місячний звіт** (`src/monthly-report.ts`, кнопки «Звіт за …» на «Головній») — Excel з аркушами: підсумок, роботи, табель, сміття, ліфтер, видачі, надходження. Суми — за ціною закупівлі, а якщо її нема (станом на листопад 2026 жодне надходження не має `purchase_price_unit`), — за поточною ціною товару з позначкою «≈».
- **Звіт для керівництва** (`src/management-report.ts` — періоди, підсумки, розмітка; `src/shell-report.ts` — перегляд `#shell-report`; кнопка на «Головній»). День / тиждень (пн–нд) / місяць, розділи вмикаються чіпами; **склад вимкнено за замовчуванням** (як у Telegram-підсумку). «Картинка для Telegram» (`html-to-image`, ленивий import): знімок `.rpt-page` у ширині 794px поза екраном (`.rpt-capture-host` — явний шрифт і без прокрутки таблиць, інакше SVG-знімок обрізає таблиці), масштаб 1.6×, довгий звіт ріжеться на рівні частини по межах розділів/рядків (`chooseImageSlices`, ≤1600 css-px ≈ ліміт Telegram 2560 px). На телефоні — `navigator.share` з файлами (якщо жест «прострочився» після рендеру, кнопка стає «Надіслати» й шле готові файли); на комп'ютері — копіювання в буфер (`ClipboardItem` з Promise) + збереження PNG. Бібліотека чекає `requestAnimationFrame`: у прихованій вкладці/панелі знімок не завершиться — це не баг. PDF робить браузер: «Зберегти PDF» → `window.print()`, стилі `@media print` у `styles.css` лишають тільки сторінку звіту; «папір» `.rpt-page` завжди світлий. При блокуванні shell звіт закривається (`onLock`).
- **Сцена будинку** (`src/house-scene.ts`, листопад 2026, вибір власника): ізометричний наш будинок — ЖК «Микитська Слобода», Шалімова 35А, змодельований за фото з двору: ліве крило виступає й обгороджує двір, позаду 4 секції уступами 22–24 поверхи, правий край заокруглений, **башточка зі шпилем — на дальньому від двору боці** (власник окремо поправив). Двір: спортмайданчик, дитячий майданчик, паркування; зліва вулиця з ліхтарями й машиною; праворуч ставок парку «Відрадний». Контур малює світна точка, вікна загоряються поверх за поверхом (група на поверх секції), відблиск по склу. Лише Web Animations API — без покадрового JS і SVG-фільтрів (перша версія з rAF і `feGaussianBlur` підвисала); тіні граней — накладання двох шарів з opacity, кольори машин — `shadeHex`, без `color-mix` (старі WebView). Дахові елементи — окремим шаром після контуру, інакше лінія даху просвічує крізь башточку. Базові атрибути = фінальний кадр: `cancel()` чи reduced motion дають повністю освітлений будинок. Палітра — `--hs-*` на `.hs-scene` у `styles.css` (день у світлій темі, вечір у `.theme-dark`).
- **Назва заставки цеглинками** (`buildBrickTitle` у `src/shell-loader.ts`, листопад 2026): кожна літера — три копії, обрізані `clip-path` на горизонтальні смуги (`.splash-brick-0..2`, межі `--c1/--c2` окремо для великих і малих літер); смуги падають знизу вгору в одному акцентному кольорі (`--md-sys-color-primary`; різнокольорові цеглинки власник відхилив — «по-дитячому»), коли складено всю назву — вона «клацає» й хвилею стає кольору тексту. Анімація — CSS `@keyframes` (затримки й зсуви в inline `--d/--s/--bx/--br`), базовий стан = звичайна назва; при reduced motion назву не розбиваємо.
- **Завантаження модуля** (`createModuleLoader` у `src/shell-loader.ts`): поки iframe активного модуля вантажиться, поверх `#shell-frames` — сцена будинку з підписом «Відкриваю …». Показ із затримкою `LOADER_SHOW_DELAY_MS` (швидке завантаження — без блимання); готовність — подія `load` iframe (`syncModuleLoader(true)` у контролері) → фінал і згасання; перехід на інший розділ — ховається одразу; запасний таймер 20 с.
- **Нижнє меню shell на телефоні**: натискання підсвічує лише пігулку іконки (`.shell-bottom-item.md-state-layer::before { display:none }`), а не прямокутник на весь пункт — на Android він мав гострі кути. Не повертати state-layer на весь пункт.
- **Налаштування shell** (`src/shell-settings.ts`, листопад 2026): тема, «Вхід за PIN», «Автоблокування» — пункт «Налаштування» в бічній панелі (спливна панель `#shell-settings`) і рядки в листі «Ще» на телефоні. Раніше ці перемикачі були лише в шапці «Журналу», і з «Головної» їх не було видно — власник вирішив, що вони «пропали». Ключі localStorage ті самі (`selected_theme`, `osbb_pin_enabled`, `osbb_auto_lock_enabled`), синхронізація з журналом — подією `storage` в обидва боки. Без PIN кнопка «Заблокувати» ховається.
- **«Головна»** (`src/shell-dashboard.ts`, `#shell-home`) — read-only зведення на сьогодні (табель, сміття, склад, роботи, ліфтер) через `createSupabaseRestClient`. Нічого не пише в базу. Нові іконки — лише з наявної підмножини шрифту (див. нижче), інакше рендериться текст назви.
- `osbb/index.html` — Виконані роботи + Ліфтер, Сміття, Зміни, Табель. Акцент — зелений (`#34c759` світла тема / `#30d158` темна). **Журнал чергувань і Графіки видалені повністю в липні 2026** (застаріла модель — вільний текст замість заявок з пріоритетом) — не відновлювати, не шукати `#section-journal`/`#section-charts` як щось загублене. **Вкладка «Заявки» (Jira, `#section-my-tickets`) видалена в жовтні 2026** на прохання користувача — не відновлювати. Усі розділи журналу доступні всім сесіям, крім «Змін» (закриті для робітників).
- `sklad/index.html` — Склад: товари, видача, інвентаризація. Теж зелений акцент (уніфіковано в липні 2026, раніше був синій).

Логіка всіх трьох модулів живе в `src/` (Vite MPA build, `npm run build` → `dist/`, деплой на GitHub Pages через `pages.yml`). HTML-файли — лише розмітка. Компонентного фреймворку немає; не переносити на React/Vue/Svelte без явного запиту.

### `src/*.ts` ↔ `src/*.js` (вересень 2026)

- Браузер і unit-тести використовують `src/*.js`; `tsc` перевіряє `src/*.ts`.
- **TS — джерело істини** для модулів із реалізацією в `.ts`: їхні `.js` **генеруються** `npm run build:js` (`scripts/build-js-fallback.mjs`, esbuild) і мають шапку `// Згенеровано з src/...`. Не редагувати ці `.js` вручну — `test:runtime` вимагає байт-у-байт збіг зі згенерованим.
- **JS — джерело істини** лише для `src/osbb-app.js` / `src/sklad-app.js` (без `.ts`, правити руками). З вересня 2026 усі контролери — повноцінний TS (shim-ів `export declare function` більше нема; не повертати їх). Спільні DI-типи контролерів (`SupabaseLike`, `ToastFn`, `KeyValueStorage`…) — `src/controller-types.ts`.
- Smoke-check шукає в `.ts`-джерелі точні рядки з анотаціями типів (`function select(button: HTMLElement)`) — при зміні сигнатури оновлювати й голку в `scripts/smoke-check.mjs`.
- Smoke-check і `tests/sklad-dom-flows.test.mjs` читають для згенерованих `.js` їхнє `.ts`-джерело.
- Сторонні бібліотеки — pinned npm-залежності (`@supabase/supabase-js`, `write-excel-file`, `html5-qrcode`, `chart.js`, `html-to-image`), не CDN. Excel/QR/графіки/картинка звіту завантажуються лениво. Excel-експорт — через `src/excel-export.ts`; xlsx видалено після аудиту, імпорту файлів немає.

## Усталені патерни дизайн-системи (не винаходити заново)

- **Кастомний `<select>`**: нативний select рендериться браузером як квадратне непіддатливе спливне меню. `enhanceSelect(select)` / `refreshEnhancedSelect(select)` тепер живуть в одному місці — `shared/enhance-select.js` (звичайний `<script src>`, без бандлера), підключені і в journal, і в sklad. Не дублювати їх назад inline — smoke-check це ловить. Обгортає прихований `<select>` кастомною заокругленою панеллю (`.custom-select-wrap/-btn/-panel/-option`), з підтримкою клавіатури (Enter/Space/стрілки/Escape) і опційним пошуком через `data-searchable="1"`. Якщо десь ще лишився голий `<select>` — використовувати той самий патерн, не робити новий.
- **Спільні CSS/JS без бандлера**: `shared/ui.css` (тултіпи `[data-tip]`, `prefers-reduced-motion`) і `shared/enhance-select.js` — єдине місце для того, що реально ідентичне між модулями. Не все дублювання варто виносити сюди: якщо модулі розійшлись у поведінці (як було з `enhanceSelect` до липня 2026, коли Sklad додав пошук), спершу звести докупи функціонально, а не сліпо взяти першу-ліпшу копію.
- **Тултипи**: `[data-tip="текст"]` замість `title=` — CSS-псевдоелемент, заокруглений темний пільс замість системного. Клас `.tip-up` — якщо кнопка всередині `overflow:hidden` контейнера (напр. в таблиці), щоб підказка відкривалась вгору і не обрізалась.
- **Skeleton-заглушки завантаження**: клас `.skel`/`.skel-bar` (shimmer-анімація) замість тексту "Завантаження..." — використовується як статичний початковий HTML у `<tbody>`, перезаписується реальним рендером.
- **Плаваюча нижня навігація** (мобільна): `#bottom-nav` / `.bottom-nav` — не суцільна смуга по краю, а картка з відступом `12px` з усіх боків, `border-radius: 26px`, тінь. У osbb позиціювання йде через Tailwind-класи (`fixed bottom-0 left-0 right-0`), тому кастомні CSS-правила для нього **обов'язково з `!important`**, бо мають перебити Tailwind-утиліти.
- **Іконки**: Shell і журнал використовують `Material Symbols Rounded` через `.material-symbols-rounded`; Sklad використовує той самий шрифт через сумісний клас `.ms`. Для нових інтерфейсних іконок використовувати офіційні назви Material Symbols, без сторонніх SVG або MDI. Шрифт постачається локально; додавши нову назву, оновити підмножину через `scripts/subset-material-icons.py` (див. `docs/audit-fixes.md`).
- **Material Design 3 — свідомий вибір напряму дизайну, не разова примха.** Користувач прямо попросив (липень 2026) дотримуватись MD3 і в майбутніх сесіях — окремо підкреслив, що йому подобаються **контури** (outlined-стиль). На практиці це означає:
  - `shared/material-tokens.css` — спільний semantic token layer для shell/journal/sklad (`--md-sys-color-*`, `--md-sys-shape-*`, `--md-sys-typescale-*`, elevation, motion, state-layer). Нові UI-полірування починати з використання цих токенів, а не додавати чергові hardcoded кольори/радіуси/тіні (напр. пріоритет замість `#f59e0b` — `var(--md-sys-color-tertiary)`, він сам адаптується під світлу/темну тему).
  - Картки/поля вводу/пункти списків — з видимим бордером. Для елементів, які мають читатись як самостійний outlined-компонент (картка статистики, пункт вибору, поле вводу) — `border:1px solid var(--md-sys-color-outline, var(--border))` (виразніший контур), а не ледь помітний `--md-sys-color-outline-variant` (той — для менш акцентних внутрішніх розділювачів/контейнерів-обгорток).
  - Кожен новий "голий" `<select>` — обов'язково через `enhanceSelect()` (див. пункт вище), інакше він рендериться нативним квадратним попапом, що ламає стиль. Те саме стосується `<input type="time">` — нативний "Засіб вибору часу" непіддатливий і не стилізується; замість нього використовувати маскований текстовий інпут `ГГ:ХХ` (`data-time-mask` + `formatTimeMaskInput`, вже є для журналу сміття й табеля).
  - Interactive-елементи (кнопки, пункти списку, картки-кнопки) — з класом `.md-state-layer` для стандартного hover/focus/pressed ripple-шару, і `:focus-visible` для клавіатурного фокусу (див. нижче) — не пропускати ні на одному новому елементі.
- **Єдині розміри й форми (листопад 2026)** — токени `--app-*` у `shared/material-tokens.css`: кнопки `--app-control-height` 48px, підпис `--app-button-font-size` 15px / вага 500 (свідомо більше за базовий MD3 — рішення «для літньої аудиторії», тепер для всього застосунку), кнопки-іконки круглі 48px з гліфом 24px, іконки навігації 24px. Радіуси: панелі/вікна/аркуші — `--app-radius-container` (28px), вкладені картки, плитки й поля — `--app-radius-tile` (16px), кнопки й статус-пігулки — full, чіпи-категорії — 8px, пункти випадних меню — 12px. Кожен модуль у кінці свого `styles.css` має блок «Узгодженість з рештою застосунку», що прив'язує його класи до цих токенів — нові кнопки додавати туди ж, а не з власними розмірами чи `font-weight:700`.
- **Без емодзі й текстових значків в інтерфейсі** (✕ ⌫ ↻ ▲▼ ◀▶ ‹› ↗) — лише Material Symbols з наявної підмножини шрифту; smoke-check це ловить. Виняток — Telegram-повідомлення з бази (`040`, там емодзі доречні).
- **Палітра й «антивайбкод» (листопад 2026, після аудиту)**: усі кольори — з однієї зеленої тональної палітри. `secondary`/`secondary-container` — сіро-зелені (не синій Tailwind, як було: через нього активне меню й тональні кнопки були сині поруч із зеленими основними). Для категорійного синього (скло, «інфо»-метрики, маркер зміни) — `--md-ref-color-info`, не `secondary`. `--md-sys-color-outline` — непрозорий колір з контрастом ≥3:1 до surface (WCAG 1.4.11; `test:m3` це перевіряє, як і те, що secondary не синій). Без hover-«підйому» карток, зеленого свічення, градієнтів «для краси» й `backdrop-filter: blur` під майже непрозорими шарами — smoke-check ловить lift/glow. Мінімальний розмір тексту в інтерфейсі — 12px (папір звіту `.rpt-*` — виняток). Тексти — на «Ви», без знаків оклику в помилках/тостах, «…» замість трьох крапок, без підзаголовків, що переказують заголовок.
- **Іконки біля заголовків карток і модулів — просто гліф кольору primary, без тонованого квадратика** (рішення власника, листопад 2026: квадратик на кожній картці — шаблонний «ШІ»-вигляд). Токена `--app-radius-icon-tile` більше нема; smoke-check це ловить. Функціональні індикатори стану (вибраний тип сміття, бейдж тосту) — не про це.
- **`!important` — лише там, де без нього змінюється вигляд** (листопад 2026: у журналі й складі прибрано ~150 зайвих; рішення приймалось вимірюванням обчислених стилів усіх елементів у світлій/темній темі, на десктопі й телефоні, у shell і окремо — відмінностей 0). Лишились: перебивання Tailwind-утиліт (`#bottom-nav`), утиліти-«вимикачі» (`.hidden`, `[hidden]`), правила для станів (`:hover`, `:focus-visible`), друк і пари правил, де одне перебиває інше лише з `!important` (напр. `html.in-shell .bottom-nav` проти `.bottom-nav` у мобільному медіазапиті). Нові `!important` не додавати «про всяк випадок» — спершу підвищити специфічність чи поставити правило пізніше.
- **Шкала тексту `--app-font-*`** (`shared/material-tokens.css`, листопад 2026): 12 / 13 / 14 / 15 / 16px для тексту, 18 — заголовки вікон і карток, 22 — заголовки розділів, 28 — заголовок сторінки й цифри PIN, 32 — головні числа статистики. Нові `font-size` тексту — лише через ці токени; `test:m3` ловить px/rem поза шкалою. Іконки (`.ms`, `*-icon`) і папір звіту (`.rpt-*`) мають власні розміри. Власна шкала складу `--text-*` прив'язана до цих токенів.

## Специфічно для Журналу (osbb): staff auth, ролі, Табель

Липень 2026 — великий рефакторинг журналу: прибрано вільнотекстовий "Журнал чергувань" і чат, додано персональний per-worker вхід поверх спільного PIN і Табель точного часу. Код ролей нижче ще живий, але фактично працює одна сесія з повним доступом.

- **Ролі** (`osbb_staff.role`): `dispatcher`, `admin`, `board` ("Правління", необмежений доступ крім Змін) — рівнозначні "повний доступ"; `plumber`/`janitor`/`electrician` — робітники, view-only календар + власні заявки. Staff-ролі "охорона" нема і не додається навмисно (просили прибрати на початку рефакторингу). **Але виконавець робіт «Охорона» (`security`) є** — додано в листопаді 2026 на прямий запит власника (`042`): лише в `completed_work` (форма, фільтр, місячний звіт, «Головна»), не в табелі й не у вході.
- `isDispatcherSession()` (`src/osbb-staff.ts`, обгортка в `src/osbb-app.js`) — єдине джерело істини, чи сесія має повний доступ: `['dispatcher','admin','board'].includes(staffSession.role)`. `WORKER_ROLES = ['plumber','janitor','electrician']`. `isTabAllowedForSession(tab)` — єдине джерело істини для видимості табів І для блокування прямого виклику `setTab()`/`requestTab()` — не дублювати цю перевірку окремо десь ще (був баг: гейтинг рахувався в двох місцях по-різному).
- **staffSession vs staffPinCache**: `staffSession` (хто ти — id/name/role) живе в `sessionStorage`, переживає reload вкладки. `staffPinCache` (сам PIN) — навмисно **тільки в пам'яті**, ніколи в storage. Наслідок: після reload сесія лишається, а PIN губиться — будь-яка дія, що вимагає server-side PIN (Табель), впаде без явного повторного логіну. Патерн виправлення — `requestStaffReauth()`: короткий екран підтвердження PIN (без вибору зі списку, особа вже відома), не скидає staffSession, тільки оновлює `staffPinCache`. Використовувати цей самий патерн для будь-якої майбутньої дії, що потребує `staffPinCache` і може викликатись після reload.
- **Табель** (`osbb_attendance`, `save_attendance_day` RPC) — точний час приходу/відходу трьох робочих ролей за день, редагує оператор. **Серверної перевірки PIN у `save_attendance_day` більше немає** (прибрано в `027`, сигнатура з `037` без `attempt`) — Табель відкритий для anon так само, як інші робочі таблиці (див. «Відомі обмеження»). Автопідрахунок годин/днів — локально з `checkIn`/`checkOut`.
- **Ліфтер** (`elevator_visits`) — окремий невеликий блок усередині вкладки «Виконані роботи» (не окремий таб): відмітки приїзду ліфтера кілька разів на місяць, день + текст що зробив, без календарної сітки.

### Технічний урок: `jsonb_set` не створює проміжні рівні шляху

Знайдено й виправлено в липні 2026 (`018_fix_attendance_jsonb_set.sql`) — вартий запам'ятати як загальний Postgres-готча, не специфічний тільки для Табеля: `jsonb_set(doc, array['a','b'], value, true)` **не створює `'a'`**, якщо його ще нема в `doc`, навіть з `create_missing = true` — той параметр створює лише **останній** елемент шляху, за умови що всі попередні вже існують. Перевірено напряму на Postgres 16:
```sql
select jsonb_set('{}'::jsonb, array['5','plumber'], '{"x":1}'::jsonb, true); -- {} (без змін!)
```
Наслідок був підступний: RPC повертав `true` (ніби успіх), а дані мовчки не зберігались — доки день хоч раз не отримає перший запис якимось іншим шляхом. Правильний патерн для дворівневого jsonb-стану "по днях": будувати вкладений об'єкт заздалегідь і `jsonb_set` лише на **один** рівень:
```sql
jsonb_set(doc, array[day_key], coalesce(doc->day_key, '{}'::jsonb) || jsonb_build_object(role, value), true)
```
Будь-де в проєкті, де jsonb-стан має вкладеність >1 рівня і оновлюється через `jsonb_set` з масивом шляху довжини >1 — перевіряти цю пастку, а не довіряти `create_missing`.

## Відомі обмеження / свідомо прийняті ризики

Щоб наступний аудит (людський чи AI) не "відкривав" це заново як несподівану знахідку — нижче задокументовані речі, які вже відомі й свідомо прийняті для поточного масштабу (один будинок, кілька співробітників), а не проґавлені баги:

- **RLS відкритий на insert/update для anon/authenticated** на "робочих" таблицях (`garbage`, `photos`, `osbb_attendance` через `save_attendance_day` без PIN, `inventory_items`, `inventory_logs`, `inventory_receipts`, `inventory_audits`, `inventory_audit_items`) — `using(true)`/`with check(true)`. Anon-ключ вшитий у публічний HTML. Обґрунтування: маленька довірена команда, PIN-екран — єдиний бар'єр перед UI, не перед даними напряму. Якщо масштаб зросте (більше будинків/користувачів) — це треба переглянути (RPC-обгортки або Supabase Auth), але зараз свідомий компроміс, не проґавлена діра.
- **Ліміт спроб PIN — по IP (`033`, `pin_throttle`)**: ключ — заголовок `cf-connecting-ip` (Cloudflare перезаписує його і блокує клієнтську підробку; перевірено на живому проєкті у вересні 2026), резерв — `sb-forwarded-for`. `X-Forwarded-For` **не використовувати** — клієнт дописує туди що завгодно. 5 помилок з IP → блок цього IP (5 хв → 15 хв → 1 год → 4 год); 30 помилок за 15 хв з будь-яких IP → блок для всіх на 10 хв.
- **PIN — не per-user авторизація.** Один спільний PIN на весь застосунок (два — для журналу: вхід/скидання). Нема аудиту "хто саме зробив дію" — поля `author`/`issued_to`/`person` це вільний текст від користувача, не перевірена особа.
- **Telegram bot-токен зберігається в таблиці `telegram_config`**, не в Supabase Edge Function secrets — це свідомий вибір (простіше міняти chat_id/токен без редеплою функцій), не помилка. Але через це RLS на `telegram_config`/`osbb_telegram_config` **обов'язково має бути без жодної policy** (default-deny) — інакше токен читається anon-ключем. Так уже сталося один раз у видаленому проєкті журналу; при будь-якій зміні цих таблиць перевіряти, що policy не додались випадково.
- **PIN-и (загальний і staff) лишаються прикладовими з SQL-файлів — свідоме рішення власника (жовтень 2026), який є єдиним користувачем застосунку.** Не нагадувати про заміну PIN, не згадувати це в звітах/аудитах і не міняти самостійно.
- ~~Немає атомарності на списанні складу~~ — **виправлено в липні 2026**: `issue_item`/`receive_item` RPC (`sklad/supabase/006_atomic_stock_issue_receive.sql`) роблять `UPDATE ... WHERE quantity >= qty` і вставку логу в одній транзакції на сервері. `sklad/index.html` більше не читає залишок з клієнтського кешу для перевірки — викликає RPC і реагує на помилку `insufficient_stock`.

## Відкриті питання на наступну сесію (липень 2026)

- **Multi-tenancy (`building_id`)** — користувач підняв питання, чи вводити поле для кількох будинків. **Не робити без явного запиту**: зараз RLS навмисно відкритий (`using(true)`) для anon в межах одного будинку (див. "Відомі обмеження" вище) — додати колонку `building_id` без реальної ізоляції (auth.uid() + членство в будинку замість спільного PIN) нічого не захистить, лише створить ілюзію multi-tenancy. Перш ніж починати — уточнити в користувача, чи справді з'являється другий будинок/клієнт, бо інакше це велика робота "про запас".
- **Storybook / візуальні тести** — вимагає компонентного фреймворку (React/Vue/Svelte). Мінімальний build-step для shell уже є, але osbb/sklad ще не компонентні, тому Storybook поки нема для чого показувати. Зараз немає окремих UI-компонентів, тільки величезні HTML-файли з дублюванням розмітки — Storybook самим собою нема для чого показувати. Реальний передумовний крок — набагато глибша компонентизація, тижні-місяці роботи, не "додати інструмент за раз".
- **Перевірити, чи виконані на живій базі SQL-файли `sklad/supabase/014`–`018`** (staff auth/Табель, роль board, лог ліфтера, два фікси `save_attendance_day` — роль board і `jsonb_set`-баг). Якщо користувач знову скаже "щось не зберігається" в Табелі — перше питання: чи виконані саме ці файли, а не одразу шукати новий баг у коді.

## Git-процес

- Кожна зміна — окрема гілка `claude/<щось>` від `main`, окремий PR через `mcp__github__create_pull_request`.
- Одразу підписуватись на PR (`subscribe_pr_activity`) і планувати self-check-in через `send_later` (~60 хв), якщо PR не змержено відразу.
- **Користувач попросив мержити PR одразу, не питаючи підтвердження** (July 2026) — це durable-інструкція для цього репозиторію, не разова.
- PR-шаблону в репо немає.
